2026-04-15 idle generation control update
- Zero-listener stations no longer refill toward full `target_queue_depth` just because bootstrap is allowed.
- When a station has no listeners, refill is now capped to `station_idle_min_ready_tracks` only.
- If the idle buffer already meets that floor, worker refill skips with `idle_buffer_healthy`.
- Newly enabled or recently updated stations get a short activation refill window and may refill toward full `target_queue_depth` even with zero listeners.
- Activation refill is still suppressed when other stations currently have active listeners, to preserve listener-first priority.
- Station playback now exposes a shared Liquidsoap unix control socket at `/var/lib/ai-radio/playback/liquidsoap.sock`.
- The station page `Skip Current` action removes the active track from queue export and forces a Liquidsoap reload, which advances to the next playable item after a short restart window.
- Important playback caveat: Liquidsoap is still configured as an always-on HLS source, so manifests can remain fresh with zero listeners. That is separate from generator load. Fully stopping playback when idle requires a listener-intent or on-demand streaming redesign so tune-in does not deadlock waiting for a manifest.

======================================================================
1) PROJECT PURPOSE
======================================================================
AIRadio is a self-hosted AI radio system that continuously generates genre-specific tracks and streams them as always-on stations.

Core goals:
- Multiple stations with distinct genre/personality profiles.
- Continuous queue refill using ACE-Step generation.
- Optional prompt/lyrics refinement through OpenWebUI.
- Playback executed by Liquidsoap (HLS output), while scheduling/business logic remains in Python.
- Web UI + API + worker orchestration + metrics/stats.

Current known station defaults:
- Synthwave FM
- Trap Afterhours
- Lo-Fi Desk


======================================================================
2) HIGH-LEVEL ARCHITECTURE
======================================================================
Services:
- api (FastAPI): orchestration API, station/state/stats endpoints, migrations.
- worker (Python loop): generation/refill, playback reconciliation, storage maintenance.
- postgres: persistent metadata/state.
- redis: queue/cache plumbing.
- liquidsoap: playback runtime and HLS segment generation.
- web (Next.js): public player/admin/stats UI.
- nginx: reverse proxy + serves HLS path.
- openwebui (separate container on host .5): prompt/lyrics refinement endpoint.
- ACE-Step Gradio server (host-level service on .5, port 7865): audio generator.

Playback boundary (important design choice):
- Python owns queue, refill logic, prompt/daypart/mood, QC, storage lifecycle.
- Liquidsoap owns actual playout + HLS publishing + now-playing sidecar outputs.

Data flow:
1. Worker checks each station queue depth.
2. If low, worker generates track(s) through ACE-Step.
3. QC + station-fit checks decide ready/failed.
4. Worker exports queue/fallback sidecars for Liquidsoap.
5. Liquidsoap plays queue and updates sidecars + HLS.
6. Worker reconciles backend state into DB/stats.

Useful SQL:
A) Latest tracks
select t.id, s.slug, t.status, t.duration_sec, t.title, t.created_at
from tracks t join stations s on s.id=t.station_id
order by t.id desc limit 20;

B) Generation metadata source attribution
select tg.track_id, s.slug, tg.created_at,
       tg.recent_context->'preprocessor'->>'source' as source,
       tg.recent_context->'preprocessor'->'diagnostics'->>'lyrics_source' as lyrics_source,
       tg.recent_context->'preprocessor'->'diagnostics'->>'prompt_source' as prompt_source
from track_generation tg
join tracks t on t.id=tg.track_id
join stations s on s.id=t.station_id
order by tg.track_id desc limit 20;

C) Ops events
select id, timestamp, service, event_type, station_id, track_id, severity, left(message,90)
from ops_events
order by id desc limit 100;

16) MAJOR UPDATES SINCE 2026-04-09
======================================================================
A) Listener-gated generation (strict)
- Generation now runs only when station has active listeners.
- Idle grace/warm-buffer generation was removed (fail-closed if listener state unavailable).
- This prevents burning GPU/storage for stations with no audience.

B) Song feedback loop (thumbs up/down)
- UI now supports thumbs up/down on now-playing and queue/recent tracks.
- API endpoint:
  POST /api/stations/{slug}/tracks/{track_id}/feedback
  body: { "session_id": "...", "vote": "up|down", "source": "web_*" }
- Station detail and now-playing include feedback aggregates + per-session vote state.
- Feedback influences generation:
  - likes bias topic/taste/mood directions,
  - dislikes add explicit avoidance constraints in negative prompting.
- Reuse scoring also accounts for promoted/signature tracks.

C) OpenWebUI title handoff enhancement
- Lyrics step now requests structured output that can include a title.
- If OpenWebUI returns title + lyrics, returned title is used as suggested track title before generator submit.
- Backward compatible with older 2-field return paths.

D) Reuse loop prevention (critical)
- Reuse fallback now dedupes by origin track id and avoids selecting origins already active in queue/recent window.
- Playback queue export also dedupes by origin id to prevent repeated source audio in cue list.
- This fixes cases where station appeared to loop same song (same source/duration) repeatedly under generation timeout pressure.

E) Storage cap enforcement hardening
- Cap remains 10GB (GENERATED_STORAGE_CAP_GB=10).
- Bug fixed: deleted tracks with detached assets could leave files on disk and inflate usage over cap.
- Cleanup now removes detached deleted-track files physically and resets DB file metadata.
- Cap pruning now estimates reclaimable bytes from actual on-disk files (not stale DB size only).
- Result: cap enforcement now actually brings usage back under configured limit.

18) FEEDBACK + TITLE FLOW (REFERENCE)
======================================================================
Track creation flow:
1. Topic chosen from station_profile.topic_ideas + taste_hints with anti-repeat logic.
2. OpenWebUI lyrics request runs first (if enabled).
3. Lyrics response can include title (preferred) and lyrics.
4. Suggested title is uniqueness-normalized against station history.
5. ACE-Step generation runs with prompt/negative/lyrics + mapped params.
6. If generation fails and fallback reuse is needed, reuse picks diverse origin candidates and avoids active-origin duplication.
